流程 Workflow
0新專案（Greenfield）
openspec/specs/ 是空的，從零開始。
↓
1proposal.md
Why + What：意圖、範圍邊界（人類語言，不談技術）。
↓
2delta specs（行為契約）
What：把意圖轉成「可驗收的行為」，寫進 changes/<id>/specs/。
新專案全部都是
## ADDED Requirements
舊專案delta 四態
## ADDED ## MODIFIED ## REMOVED ## RENAMED
↓
3design.md
How：技術選型、架構決策與理由。
↓
4tasks.md
Steps：可逐條打勾的實作清單。
↓
5implement /opsx:apply
照 tasks 實作，可隨時回頭修改 change 內任何文件。
↓
6archive /opsx:archive
delta 合併進 specs/ → Source of Truth 更新，change 移入 archive/。
↓
✓有 Source of Truth 的專案
openspec/specs/ 更新完成，從此每一次改動都由此進入下一個 change。
🔄 同一個 change 內：流動式修改，不是「從頭來」
在 design / tasks / implement 任何時候發現問題，只回去改受影響的那一份 artifact，其他已完成的不用重做：
scope 變 → proposal.md　需求變 → spec.md　技術決策 → design.md　多了工作 → tasks.md。
OpenSpec 用 status 個別追蹤每份 artifact 是否 done，只有被牽連的才要重新確認。
➡️ 完成之後：開「下一個 change」（全新一輪，不是打掉重練）
archive 後 SoT 更新完成，下一次修改是一個新的 change folder。
改動小 → proposal / design 寫得精簡即可；但仍跑同一套流程，OpenSpec 不會讓你跳過 artifact。
資料夾結構 openspec/
← 可左右滑動檢視完整路徑 →
📂openspec/
├─ ⚙️config.yamlschema / context / rules — 給 AI 的專案脈絡與規範
├─ 📂specs/✅ Source of Truth
│  ├─ 📄auth/spec.md
│  ├─ 📄vehicles/spec.md
│  ├─ 📄audit-log/spec.md← archive 後由 delta 併入
│  └─ … 每個 capability 一個資料夾（employees / dashboard / web-shell）
└─ 📂changes/🚧 變更工作區
   ├─ 📂2026-05-29-add-audit-log/進行中的 change（日期-slug）
   │  ├─ ①proposal.mdWhy + What
   │  ├─ ②specs/audit-log/spec.md
   │  │    delta：ADDED / MODIFIED / REMOVED / RENAMED（可含多個 capability）
   │  ├─ ③design.mdHow
   │  ├─ ④tasks.mdSteps
   │  └─ ⚙️.openspec.yamlschema + created
   └─ 📦archive/⑥ 完成後整包 change 移來這
      └─ 📂2026-05-28-add-vehicle-management-system/
         … proposal / design / tasks / specs（多個 capability）
⑥ archive 同時做兩件事：把整包 change 移進 changes/archive/，
並把它 specs/ 的 delta 合併進根目錄 specs/，讓 Source of Truth 永遠反映「現況」。
specs/ = 現況（已實作） changes/ = 提案（草稿/進行中） 📂 資料夾
