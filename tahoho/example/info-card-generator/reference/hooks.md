# 內容策略：封面公式與排卡模板

> 這份文件回答兩個問題：封面怎麼寫才會讓同仁停下來看、整副牌怎麼排才會被看到最後一張。
> 鐵律：**所有數字、條號、金額必須出自素材或可考證**。查無來源 → 換非數字公式，不准編。

## 一、封面公式（六選一）

| # | 公式 | 結構 | 範例骨架（DSL） | 使用條件 |
|---|------|------|----------------|----------|
| 1 | 數字反差 | N 件退件裡 M 件是 A | `# !!8 成!!退件`<br>`# 都卡在==同一條==` | 數字可考證（稽核、統計表），否則禁用 |
| 2 | 痛點提問 | 做完 X 就以為結束了？ | `# 報價附了`<br>`# 就能!!送簽!!？` | 痛點必須是同仁真的會踩的 |
| 3 | 認知顛覆 | 你以為 A，其實 B | `# 你以為金額算單年`<br>`# 其實看==全期累計==` | B 要在內容卡裡撐得起來 |
| 4 | 清單承諾 | N 條 X，一次看完 | `# 送簽前`<br>`# 先自檢 ==5 條紅線==` | N 與實際內容相符（lint 會核對「N 張」） |
| 5 | 身分呼喚 | 給第一次 X 的你 | `# 給第一次`<br>`# ==送提案單==的你` | 受眾輪廓明確（新人、新主管）時最有效 |
| 6 | 時間承諾 | N 分鐘搞懂 X | `# !!90 秒!! 搞懂`<br>`# ==核決層級==` | 內容真的能在短時間讀完 |

封面必備三件套：`[badge]` 定調（文件名 · 版本或年份）、主標（至少一處 `!!` 或 `==`，lint 強制）、一句副標把「看完能得到什麼」說完整。

### 封面準則：先講「跟我有什麼關係」，再講結論

封面不是摘要，也不是文件標題頁。封面只做一件事：讓對的同仁覺得「這就是我常卡的地方」，然後願意翻下一張。

1. **同仁的處境**：把素材裡真實的退件理由、常見誤解、卡關點放到主標。例：「提案單被退回補件，多半是這幾條沒看到。」
2. **口語短句**：用人會說出口的句子，不用條文語氣開場。「第 3 條核決權限」是內容卡的標題，不是封面。
3. **易讀**：主標 2 行以內，每行約 8–13 字；副標 1–2 短句，每行約 20 字內。標記膠囊不要跨太長的句子。
4. **副標只補刀**：副標不解釋全文，而是補一個轉折或承諾。例：「看完這 5 張，送件一次過。」

封面 rewrite 對照：

| 情境 | 不夠好的寫法 | 更好的寫法 |
|------|--------------|------------|
| 像文件標題 | `# 採購與簽核規範重點` | `# 送簽前`<br>`# 先自檢 ==5 條紅線==` |
| 條文語氣 | `# 第 5 條 比價規定` | `# 50 萬以上`<br>`# 沒!!三家報價!!會被退` |
| 缺少讀者視角 | `# 核決層級說明` | `# 你這案`<br>`# 到底==誰來核==？` |

## 二、排卡結構模板（四選一）

**規範型**（制度、內規、SOP）
```
1 @cover   封面：同仁最常踩的點
2 @point   先講最重要的一條（門檻、層級）：[flow] 或編號盒
3–5 @point 每卡一條規則：[ok]/[no] 對照、條列盒、[warn] 例外
6 @point   最常見的退件原因：> 引言（原文）＋ 說明
7 @summary 自檢清單（條列）＋ 依據：文件名、條號
```

**教學型**（觀念 → 方法）
```
1 @cover   封面
2 @point   痛點共鳴：列出同仁正在踩的坑（編號盒）
3 @point   觀念翻轉：舊做法 vs 新做法（[flow] 或 [ok]/[no]）
4–6 @point/@code 方法步驟：一卡一步，有指令或設定就上 @code
7 @summary 重點回顧＋下一步
```

**清單型**（N 個 X）
```
1 @cover   封面（清單承諾）
2 @point   為什麼重要／怎麼挑的
3–6 @point 清單本體：每卡 2–3 項，用條列盒，不要一卡塞完
7 @summary 從哪一個開始（給行動起點）
```

**對比型**（錯誤 vs 正確）
```
1 @cover   封面（痛點提問）
2 @point   錯誤示範：[no] + 後果
3 @point   正確示範：[ok] + 原理
4 @point   為什麼差這麼多（[flow] 拆解）
5 @summary 自檢清單（條列）
```

## 三、每卡規則

- **3 秒測試**：只看大標（##）能否知道這卡在講什麼。不行就重寫標題。
- **一卡一概念**：一張 @point 只允許一個 `##`（lint 強制）。想講兩件事就拆兩張。
- **字數上限**：cover ≤ 60、point ≤ 160、summary ≤ 100（criteria 可調；計字不含 badge 與程式碼）。
- **結構優先**：內容盡量落在元件裡（清單盒、對照盒、flow、引言），避免整卡裸段落——與 course-page-generator 的「避免 loose-text」同一原則。
- **節奏**：相鄰兩卡的主元件換版型（lint 會提醒）。連續兩卡都是編號盒，翻起來像同一張。
- **引原文**：規範、決議這類素材，關鍵句用 `> 引言` 保留原文，不要改寫成自己的話再讓人去對條文。
- **流程卡只給流程，`*` 只給重點**：`[flow]` 用在有先後順序的事（步驟、簽核鏈、before → after）；`*` 標的是這張卡的文字在講的那一步，不是最後一步。
  - 好：`[flow] 讀懂 -> 定規則 -> MVP -> 自測 -> *反例驗收 -> 給使用者試`，搭配 `[warn] AI 說通過不算數，要親手打開`——亮的那格就是 warn 在講的事。
  - 好：`[flow] 部門主管 -> 總經理 -> *董事會`，搭配「300 萬以上要送董事會」——亮的是門檻。
  - 不好：`[flow] 頭像 -> Settings -> *Privacy`——導覽路徑，終點本來就是終點，不用亮；拿掉 `*`。
  - 不好：每張 flow 卡都把最後一格標 `*`——讀者會以為終點永遠最重要，強調就失效了。

## 四、結尾卡（@summary）公式

`重點回顧 ＋ 下一步 ＋ 依據`

- 重點回顧：3–5 條自檢清單或一句金句（條列／`[tip]`／引言 擇一，lint 強制）
- 下一步（選用）：該找誰、該填哪張表、該去哪個資料夾
- 依據：`依據：<文件名 版本> 第 N 條`（`require_source: true` 時 lint 強制）——讓同仁看完能回到原文核對，也讓卡片有版本可追

## 五、產出後自檢（跑 lint 前先人工過一輪）

- [ ] 封面是不是同仁會說出口的話，而不是文件標題？
- [ ] 封面主標是否 2 行內、每行 8–13 字左右？
- [ ] 每個數字、條號、金額都指得出來源？
- [ ] 有沒有 AI 腔（以下是、總而言之⋯⋯）？
- [ ] 每張卡拿掉其他卡單獨看，還有價值嗎？
- [ ] 結尾卡的依據寫的是「現行版本」嗎？
